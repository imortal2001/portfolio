kusinalink.expo.app

2026 · Client project · Ordering platform

KusinaLink

Daily-menu ordering for a restaurant that delivers lunch to an office — in daily use.

Problem
Orders came in over chat. The cook guessed quantities, dishes sold out mid-order and every packed meal had to be matched to a name by hand.
Approach
Expo and Supabase with row-level security. Stock is deducted inside an atomic Postgres function, orders snapshot name and price, and the kitchen gets per-dish totals and a handover list.
Outcome
Overselling is impossible by design, the kitchen cooks to real numbers, and releases ship with one verified deploy command.

Expo · React Native · TypeScript · Supabase · PostgreSQL · EAS Hosting

jammr.kan0.workers.dev

2026 · Solo · Realtime web & mobile

Jammr

A group chat where friends hear the same song at the same moment, on the web or on their phones.

Problem
Listening together over a call means one person shares their screen and everyone else hears compressed audio, out of sync.
Approach
One Durable Object per room owns state and WebSockets. Clients estimate clock offset NTP-style and correct drift; songs are matched through a quota-aware pipeline with caching.
Outcome
Browsers and phones stay within 1.5 s of each other, with no servers to manage, on Cloudflare’s free tier.

Cloudflare Workers · Durable Objects · WebSockets · JavaScript · React Native

03 Engineering decisions

Trade-offs behind the work

The parts that took the most thought, and why I solved them the way I did.

  1. Sync without streaming

    The server never streams audio or a playhead. It stores “position P at server time T”; each client estimates its clock offset and corrects drift over 1.5 s, and new songs start 1.5 s in the future so every device can buffer first.

    Jammr

  2. Correctness in the database, not the client

    Stock is deducted in one atomic Postgres function at the moment of ordering, so two customers racing for the last serving can’t both win. Orders snapshot name and price so later edits never rewrite history.

    KusinaLink

  3. Rules engine apart from rendering

    All game rules live in a pure, renderer-free module with Vitest coverage. Saves are versioned and migrated forward through six versions, so every content update shipped without resetting progress.

    Isla Lola

  4. Designing around a hard quota

    YouTube allows about 100 searches a day. Matching tries free sources first — MusicBrainz by ISRC, then official artist channels — caches every result and pre-matches chart songs on a cron.

    Jammr

  5. Deploys you can trust

    The host sometimes kept serving the old build after a release. The deploy script stamps each build with an ID, polls production for it and re-promotes until the new version is really live.

    KusinaLink

  6. Localisation with intent

    A small i18n layer ships the UI in English, Filipino, Cebuano, Ilocano and Hiligaynon, with a glossary that deliberately keeps the characters’ Taglish dialogue as it is.

    Isla Lola

04 Approach & skills

How I work

  1. Agree on “done” first

    Who it’s for, what success looks like and what’s out of scope — written down before code.

  2. Model the data early

    Flows and data model before screens; decisions stay cheap while they’re still on paper.

  3. Ship in small slices

    Working features on a live preview every few days, behind tests and migrations.

  4. Own it after launch

    Verified deploys, documentation and iteration based on how people actually use it.
